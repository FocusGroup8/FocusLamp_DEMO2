# 摄像头优化第一批

本批未执行固件编译、烧录、镜像构建或容器重启。Python 仅做 AST 语法检查，不代表实机验收通过。

## 修改

- head：metadata 与 JPEG 共用 1500ms 试验发送预算（2026-10-16 从 400ms 调整），采用每次调用的非阻塞发送，不改变 HTTPD socket 的全局阻塞模式。整组累计两个 WS 头和两个载荷的已写字节。
- 仅预算耗尽且整组累计为 0 字节时，丢当前帧并保留连接，返回 ESP_ERR_TIMEOUT；计入 total_failed/consecutive_failures 供 BBA 降档，不计入踢客户端的失败阈值。整组已写出任何字节，或发生连接错误（即使零字节），立即 shutdown 并 kick，不等待失败阈值。其他非整组调用仍为失败即关闭。
- 原因 BUDGET_TIMEOUT/CONN_ERROR 与动作 DROP_KEEP/CLOSE 分开记录；Camera group 日志最多每 10 秒一次（首次立即），包含本次 bytes/dur_ms/errno 和开机累计 budget/conn/zero_drop/closed。瞬时 EAGAIN 继续按剩余预算等待，不单独算失败。日志不是每次失败的逐条记录。
- 帧率：LOW 2、MID/HIGH 5 FPS；用户设置为上限；同步降低 PI 目标码率，保留原 JPEG 质量档位。低档升档采样门槛同步改为 2。
- Docker：接收循环只替换最新待处理帧；独立任务预处理并推送；各浏览器并行发送，单次包组超时 400ms，慢客户端关闭。
- 欢迎语 1、2、3 替换为三条具体文案并附简短朗读指令。云端是否照读仍需实际听取。
- 每算法在途限制属于第二批，未实施。本批处理中的帧和一个最新待处理帧同时存在，旧待处理帧被覆盖，不承诺每帧保留。

## 生效

head 源码位于 C:/Users/Administrator/Desktop/try_PZF/head，需要用户自行编译并烧录 head；本批不需要重烧 controller。

Docker 源码位于 D:/Docker_demo2/docker/main-client/main.py。Dockerfile 使用 COPY，没有源码挂载，单纯点击启动或重启不会更新镜像。用户准备测试时在 PowerShell 执行：

```powershell
cd D:\Docker_demo2\docker
$env:ESP32P4_IP = '10.87.104.143' # 仅在 head 当前 IP 仍为此值时使用
docker compose up -d --build --no-deps main-client
```

这条命令会构建并重新创建 main-client，但不会启动算法依赖。此前 Docker 接收与推送解耦若已经部署，本次无需再次构建；本次未改 Docker。

当前复测顺序：先单独更新 controller，用户已确认基座板为 COM6，关闭摄像头传输验证语音 C3；再更新 head 验证本次摄像头调整；最后合并开启摄像头和算法做语音对照。head 端口需按实际连接确认，不使用 COM6 烧录 head。

## 验收

每阶段运行 5 分钟，记录网页 FPS、head Stats 的 avg_dur/last、摄像头重连次数和同一时段 ping。目标为健康链路接近稳定 5 FPS，拥堵降到 2 FPS；开屏和调亮度仍能响应。

1500ms 是待验证参数，不保证达到 5 FPS：健康时目标为 5 FPS，拥堵时允许降至 2 FPS 或更低的实际吞吐。若仍频繁 CLOSE 或单次耗时明显超预算，保留 head Camera group/Stats 和 Docker 同时段日志继续定位，不能只由 ping RTT 推出发送耗时。总时长仍受任务调度和 ESP-Hosted 调用实际行为影响，需以日志验证，不能仅凭源码声称绝对实时保证。
