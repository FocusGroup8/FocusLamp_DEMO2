# L5.4 专注 / 陪伴：状态与计时迁移

## 本批已实现

- controller 本地专注计时，时长 1–180 分钟；默认 30 分钟。
- 陪伴状态，无自动结束时长；专注与陪伴互斥切换。
- 对话期间暂停专注倒计时；真正结束对话或断连后恢复。
- `device_state.app_state` / `voice_active` 接线；原有四个 MCP 工具名不变。
- `GET /api/mode` 查询，`POST /api/mode` 控制；两个 handler 占原有 HTTP server
  最后两个槽（10 + 2 = 12），容量配置不变。两次注册均检查返回值。

本批**不联动**灯带、光感、雷达提醒、触摸、LCD、白噪声或机械臂，也不向 head
同步模式。陪伴呼吸灯仍通过已经可用的 `self.focuslamp.led.set_effect` 单独控制。
HTTP 与 MCP 都明确返回 `state_only=true`，不得把状态成功解释为外设已执行。
基座屏幕留第 6 批；不会把基座 SPI 小屏与 head 显示接口混为一谈。

## 计时与内存

使用共享 `esp_timer` 的 1 秒回调，不新增任务/任务栈；按真实微秒结算经过时间，
而不是每个回调简单加一秒。暂停前的不足一秒余量保留，恢复不补扣暂停时间。
剩余秒向上取整；到期置 `idle`、剩余 0，保留 `completed=true` 供查询。

模块初始化排在 `xiaozhi_manager_start()` 调用之后，不改 OPUS 预创建、AFE、
mic 或舵机驱动。异步麦克风初始化仍可能在进行；这不是内存容量保证。
已有解码器在启动时创建并保留，不要求随后空闲最大块一直大于 17,784 字节。
实际回归仍应确认 OPUS 创建成功、语音有声、后续初始化没有新失败。

聊天状态直接在短锁下更新；单槽 overwrite 队列仅供异步日志，不参与计时正确性。
`TTS stopped — continuing conversation (listening)` **不代表对话结束**，此时仍暂停。
必须等 `Audio channel closed`，或通过原有 `/api/chat/end` 结束对话，才恢复。

## 编译 / 烧录

仅编译并烧录 **controller**（当前在原基座 PCB 上运行）；head/base/voice 不重编译。
本轮仅做四个 C 文件的 ESP-IDF 编译参数语法检查，没有完整构建或烧录。
主机编译器仅支持 RISC-V/Xtensa，因此未执行主机端控制时钟测试；不能把语法检查
当作计时实测。下面的上板三项才是运行验收。

启动应出现：

```text
OPUS decoder prepared at startup (internal RAM, retained for TTS)
Mode controller ready: state/countdown only, timer=1 s, no hardware effects
GET/POST /api/mode registered (state/countdown only)
```

## 上板验证（PC 必须连同一个热点）

从本次串口 `Got IP` 取 controller 的实际 IP，不沿用旧地址。
PowerShell 中先设置 `$ctl`，以下 `<实际IP>` 须替换：

```powershell
$ctl = "http://<实际IP>"
curl.exe --max-time 8 -i "$ctl/api/device/info"
curl.exe --max-time 8 -i "$ctl/api/mode"
```

初始应是 `200`、`mode=idle`。如果模式模块初始化失败，查询应为 `503`，
不能假报已就绪。尚未注册则为 `404`，应检查两条注册日志。

### 1. 模式与计时

先结束可能仍在监听的对话，再开一轮一分钟专注：

```powershell
'{}' | curl.exe --max-time 8 -i -H "Content-Type: application/json" --data-binary '@-' "$ctl/api/chat/end"
'{"mode":"focus","duration":1}' | curl.exe --max-time 8 -i -H "Content-Type: application/json" --data-binary '@-' "$ctl/api/mode"
curl.exe --max-time 8 -i "$ctl/api/mode"
Start-Sleep -Seconds 5
curl.exe --max-time 8 -i "$ctl/api/mode"
```

应为 `mode=focus`、`app_state=3`、`voice_active=false`、`paused=false`，剩余约
60 → 55 秒（网络往返会消耗时间）。不再唤醒时，约 60 秒有效计时后应变为
`mode=idle`、`remaining_sec=0`、`completed=true`，串口出现 `Focus completed`。

### 2. 对话暂停与恢复

重新开一轮一分钟专注，待剩余开始递减后唤醒并对话。聊天期间隔几秒查询两次：

```powershell
curl.exe --max-time 8 -i "$ctl/api/mode"
Start-Sleep -Seconds 5
curl.exe --max-time 8 -i "$ctl/api/mode"
```

应为 `voice_active=true`、`paused=true`，两次 `remaining_sec` 一致。
播报结束后若仍监听，继续暂停是正确结果，不应视为卡住。

```powershell
'{}' | curl.exe --max-time 8 -i -H "Content-Type: application/json" --data-binary '@-' "$ctl/api/chat/end"
Start-Sleep -Seconds 5
curl.exe --max-time 8 -i "$ctl/api/mode"
```

应恢复 `voice_active=false`、`paused=false`，剩余继续递减。断连也应清除聊天暂停。

### 3. 陪伴与停止

```powershell
'{"mode":"companion"}' | curl.exe --max-time 8 -i -H "Content-Type: application/json" --data-binary '@-' "$ctl/api/mode"
curl.exe --max-time 8 -i "$ctl/api/mode"
'{"mode":"idle"}' | curl.exe --max-time 8 -i -H "Content-Type: application/json" --data-binary '@-' "$ctl/api/mode"
```

陪伴应为 `app_state=4`，没有倒计时；切入陪伴终止先前专注，不会两模式并行。
`idle` 清除会话与完成标记。重复陪伴 start / stop 幂等；重复专注 start 返回
`409` 且不重置进度。各自 MCP stop 只停止对应模式，不会误停另一个模式。

语音仍用原四个工具：`self.focuslamp.focus.start/stop`、
`self.focuslamp.companion.start/stop`。语音中启动专注会立即因当前对话而暂停，
这是设计行为，需结束对话后才计时。无需 head 在线。

## 最小负向与回归

- `{"mode":"focus","duration":0}`、`181`、小数、非法模式 / 非 JSON → `400`。
- 超长 body → `413`；读取超时 → `408` 并退出，不无限重试。
- 不修改 SDK 配置、分区、发现组件、音频/唤醒/舵机/触摸驱动。
- 穿插一次播报与已通过的机械臂动作，确认仍有声，无新 OPUS 分配失败或 panic。
- 不要求每秒刷日志；模式汇总每 30 秒，实时剩余通过 GET 查询。
