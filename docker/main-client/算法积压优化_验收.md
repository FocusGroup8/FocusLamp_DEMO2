# 电脑端算法积压优化

## 本次范围

只修改 main-client 的常规连续识别派发。每算法最多一个 worker（含等待原有全局信号量的请求）和一个最新待处理帧；过载时覆盖旧 pending，不重试旧帧。图像、设备时间戳、帧号、PC 接收时间、附带参数作为同一份载荷更新。

VLM 两种调用保持原路径；没有启用服务。未改跳帧配置、算法超时、预处理方向、网页推送逻辑、head、语音。新模块使用 Python 标准库，不新增安装依赖。

同一个事件循环内派发及退出交接没有 await，不新增 per-algo 锁。异常后继续处理最新 pending；取消时清空该 worker 的 pending 并记丢弃，后续新帧可以重新启动。程序结束时取消并回收这些 worker。

## 诊断口径

GET `/results` 保留原 success/results，新增 `algorithm_diagnostics`。持续收图时每约 10 秒也输出一次 `Algorithm backpressure`。

- `worker`：0/1，该算法后台任务是否存在。
- `inflight`：0/1，是否已取走载荷，包含等待全局信号量，不等同于 HTTP 已发送。
- `queued`：0/1，是否存在最新 pending。必须分别满足 inflight≤1、queued≤1；合计可为 2。
- `dropped`：开机累计被覆盖或取消清理的 pending 数；不是网络丢包，也不是检测失败次数。正常运行可为 0，受控过载才要求增长。
- `errors`：worker 捕获的未处理普通异常数；不等同于 HTTP 失败数，已有 HTTP 错误仍由原路径记录。
- `result_age_ms`：最近一次成功结果写缓存时，减去该载荷的 PC 接收单调时间；包含本机预处理、排队、等待信号量和请求，不含板端采集与网络传输到 PC 的耗时。无成功结果时为 null，失败时保留上次值。
- `result_frame_seq`：上述成功结果对应的帧号。年龄是该结果完成时的耗时，不是当前缓存已陈旧多久；结合帧号是否继续推进判断。

## 已执行的离线验证

运行 `python -B test_algorithm_dispatch.py`。测试加载真实调度及 main.py 调用路径，但用假 HTTP/可控阻塞，不打开摄像头、不连接板子、不调用实际算法或收费服务。

覆盖正常无丢弃、过载只取最新、附带参数快照、全局信号量等待、异常后继续、运行中取消、首步前取消、再次派发、单调时钟年龄、关闭清理、多算法独立、无结果清理、跳帧/VLM 原路径、HTTP 超时与信号量、接收时间传播、结果接口兼容。

受控过载：301 次输入，只执行初始帧和每轮最新帧（13 次），覆盖 288 次，峰值为 1 个算法 worker，最终处理帧号 300。这只证明调度有界，不是实际推理吞吐/FPS 基准，也不是 5–10 分钟真实视频测试。

## 生效与后续验收

本轮不构建镜像、不重启容器。现有 Dockerfile 使用 COPY，点击重启不会加载源文件；准备联调时自行执行：

```powershell
cd D:\Docker_demo2\docker
docker compose up -d --build --no-deps main-client
```

保持现有 ENABLED_ALGORITHMS 不变，不为测试启用 VLM。使用电脑摄像头或真实录制视频持续 5–10 分钟，先正常负载，再通过隔离测试模拟慢算法。检查各算法任务与槽位有界、结果帧号推进、接收至结果耗时不持续发散。网页原图 FPS、算法结果更新率和板端发送 FPS 必须分开看。

尚无 head，不能据离线测试认定热点、板端发送、实际模型耗时或端到端卡顿已解决。若一个正在执行的请求本身很慢，它仍会等待原有 HTTP 超时；本次不取消在途推理，只丢旧待处理帧。
