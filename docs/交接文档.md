## 1. 整体介绍及版本关系

### 1.1 DEMO2 是什么

FocusLamp 是一个「专注灯」系统：由 **ESP32-P4 灯头板** 采集摄像头画面（也可用 PC 本地 USB 摄像头替代），把画面推送给 **PC 端算法服务**；算法服务完成人脸/情绪/疲劳/专注度/姿态/手势/玩游戏等检测后，把结果回传，用于驱动灯具的表情、灯光、机械臂与语音反馈。

**DEMO2 是第二版算法端**，定位是在 DEMO1 的基础上扩充算法能力，并首次打通「算法端 → ESP32」的结果回传链路。

| 项 | 内容 |
|----|------|
| 工程根目录 | `d:\Docker` |
| 组成 | Docker Compose 微服务工程（`docker/`） + 单机版检测器（`algorithm/FocusDetector/`） |
| 算法服务数量 | 12 个算法微服务（其中 10 个在当前 `docker-compose.yml` 中启用，2 个为遗留参考实现） |
| 图像帧来源 | ESP32-P4 `/camera`（默认）或本地 `camera-capture`（`profiles: camera`） |
| 结果消费 | PC 端 Web UI（`http://localhost:9000`） + ESP32-P4 `/algo`（JSON-RPC 2.0） |
| 技术形态 | Docker Compose 微服务 + 单机 Python 工程 |

### 1.2 版本关系（DEMO1 → DEMO2 的演进）

DEMO2 是在 DEMO1 基础上演进而来，主要变化：

1. **算法服务扩充（6 → 12）**：DEMO1 的 6 个算法（head-pose、gesture、focus、emotion、fatigue、face-detector）在 DEMO2 中扩展为 12 个。
   - **新增 6 个**：`gesture-mantis`（手势 + 组合手势）、`pose-detector`（姿态 + 颈部运动）、`face-landmarker`（人脸网格）、`face-position`（面部空间坐标）、`vlm-visual-qa`（豆包 VLM 视觉问答）、`vlm-game-detector`（YOLO + 手部接触 + 豆包 VLM 判定玩游戏）。
   - **重写**：`focus` 由 DEMO1 的「YOLO + MediaPipe FaceMesh 头部偏航」改为「Mantis/engage ONNX + MediaPipe 五官/手势 + 番茄钟窗口管理」。
   - **降级为遗留参考实现**（目录保留，但**未在当前 `docker-compose.yml` 中定义**）：`gesture`、`head-pose`。
2. **通信协议升级（关键差异）**：DEMO1 的算法结果仅在 PC 端本地消费；DEMO2 新增 ESP32 `/algo` WebSocket 通道，算法结果以 **JSON-RPC 2.0 `tools.call` / `algorithm.result`** 形式回传给灯头板。详见第 7 章。
3. **摄像头帧协议补全**：ESP32 `/camera` 端点每帧先发文本帧 `{"type":"frame_header","seq":N}`，再发二进制 JPEG；算法端据此做丢帧/乱序检测。
4. **新增单机版工程**：`algorithm/FocusDetector`（PyPI 包名 `FocusDetector`，v0.2.0），不依赖 Docker 与 ESP32，直接在 PC 上跑本地摄像头做专注/行为检测演示与算法验证。
5. **工程健壮性增强**：DEMO2 的 `docker-compose.yml` 增加健康检查（`x-healthcheck`）、日志轮转（`x-logging`）、内存/CPU 限制（`mem_limit`/`cpus`）、`tmpfs`、`profiles` 等生产化配置；主控新增算法忙碌跳过（返回 503）、`skip_frames` 降频、`forced_algorithms` 强制启用等机制。
6. **端口策略调整**：DEMO1 把每个算法端口都发布到宿主机以便单服务调试；DEMO2 的算法容器**只走 Docker 内部网络**，仅 `main-client`(9000) 与 `camera-capture`(9007) 发布宿主机端口。

> 版本关系判断依据：两个工程的 `docker-compose.yml`、`README.md`、`KNOWLEDGE_BASE.md` 与算法服务实现互相对应，DEMO2 是 DEMO1 的超集与协议升级版。

工程根目录：`d:\Docker`（也是 DEMO2 仓库根目录）

```

│       ├── focus\                   # 专注度/参与度（容器内 9003）

│       ├── main.py                  # 入口，读取 config/main.yaml
│       ├── pyproject.toml           # 包定义与依赖
│       ├── README.md / REPORT.md    # 说明与设计报告
│       ├── docs\                    # 设计文档（face_position_design.md 等）
│       └── test_*.py                # 算法验证脚本（豆包 API / YOLO / 人脸网格等）
```

## 7. DEMO2 整体运行流程

### 7.1 数据流

```
[ESP32-P4 灯头板  :80]
   ├─ /camera ──► 文本帧 {"type":"frame_header","seq":N}  +  二进制帧 JPEG
   │                        │
   │                        ▼
   │              [main-client :9000]  ←──(或──  camera-capture :9007 本地摄像头)
   │                        │
   │                        ├─ 解码 JPEG、按 skip_frames 调度
   │                        ▼  POST /detect_visualize (base64 图像 + timestamp)
   │          ┌─────────────┴───────────────────────────────────────────┐
   │          │ focus 9003 · emotion 9004 · fatigue 9005 · face-detector 9006    │
   │          │ gesture-mantis 9009 · pose 9010 · face-landmarker 9011    │
   │          │ face-position 9012 · vlm-visual-qa 9013 · vlm-game-detector 9014│
   │          └─────────────┬───────────────────────────────────────────┘
   │                        │  result 子对象 + visualized_image
   │                        ▼
   │              [main-client Web UI  http://localhost:9000] 展示可视化
   │                        │
   └── /algo ◄──────────────┘  JSON-RPC 2.0 tools.call → algorithm.result
                               （每 ALGO_SEND_INTERVAL 默认 1.0s 回传一次）
```

要点：

- `/camera` 与 `/algo` 是两条独立 WebSocket 连接：前者只收帧，后者只发结果。
- 算法结果**同时**送到 PC 端 Web UI（可视化）与 ESP32 `/algo`（驱动灯具），两条链路互不阻塞。
- 算法端在 1.0s 内只回传一次结果（`ALGO_SEND_INTERVAL`），避免高频刷屏。

### 7.2 算法结果回传（`/algo`）协议要点

**算法端 → ESP32（请求）**

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools.call",
  "params": {
    "name": "algorithm.result",
    "arguments": {
      "focus": {"engage_level_name": "Engaged", "focus_level_name": "HighFocused", "focus_score": 0.85},
      "emotion": "happiness",
      "fatigue": 2,
      "gesture": "Thumb_Up",
      "vlm_game_detector": {"judgment": "yes", "trigger_source": "phone", "reason": "..."},
      "presence": {"present": true, "duration_s": 65.0}
    }
  }
}
```

**ESP32 → 算法端（响应）**

```json
{ "jsonrpc": "2.0", "id": 42, "result": { "content": [{"type": "text", "text": "{\"ok\":true}"}], "isError": false } }
```

**字段取值约定（以算法端当前代码为准）**

| 字段 | 取值 | 来源 |
|------|------|------|
| `vlm_game_detector.judgment` | `yes` / `no` / `uncertain` / `pending`（未触发）/ `error`（API 异常） | `docker/algorithms/vlm-game-detector/server.py`（豆包返回中文后经 `JUDGMENT_EN_MAP` 转为英文） |
| `vlm_game_detector.trigger_source` | `phone` / `computer` / `null`（无接触） | 同上 |

> 历史说明：`judgment` / `trigger_source` 早期曾约定为中文（`是`/`否`/`不确定`、`手机`/`电脑`），算法端现已统一改为英文枚举；ESP32 端需同步适配，详见第 4 章「ESP32 端 VLM 字段英文协议适配」。如需再次变更，须与硬件端共同确认并修订协议文档。

其他要点：

- `frame_header` **不含 `timestamp` 字段**（ESP32 未集成 SNTP），算法端在字段缺失时回退使用本机 Unix 时间戳。详见第 4 章「ESP32 帧序列问题报告与解决建议」。
