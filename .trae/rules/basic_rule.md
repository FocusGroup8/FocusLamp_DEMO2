# SOLO 模式阶段门控任务编排规则

## 一、模式定义

**SOLO (Stage-gated Orchestration for Long Operations)** 模式是一种面向复杂多步骤工程任务的人机协作提示词设计模式。通过 **目标声明 -> 分阶段流程 -> 全局约束** 的三段式架构，将开放式任务转化为可控、可验证的 AI 协作流程。

### 核心范式
```
目标声明(WHAT) -> 阶段化流程(HOW) -> 约束边界(BOUNDARY)
```

### 执行流
```
[开始] -> [阶段1] -> [确认闸门] -> [阶段2] -> [确认闸门] -> ... -> [阶段N] -> [确认闸门] -> [结束]
```

---

## 二、结构规范

### 2.1 三段式架构（必须）

| 段位 | 功能 | 位置规则 | 必要程度 |
|------|------|----------|----------|
| 目标声明 | 定义任务范围、边界与最终产出 | 文档起始第1行 | 必须 |
| 分阶段流程 | 将任务拆解为可执行的子步骤序列 | 第3行起，占据文档主体 | 必须 |
| 全局约束 | 设定行为规范、交互方式、角色边界 | 流程之后，文档末尾 | 必须 |

### 2.2 阶段内部子结构（必须）

每个阶段必须包含三级结构：

1. **阶段标题**：使用 `### 阶段N：[阶段名称]` 格式
2. **动作清单**：使用有序列表，每项包含：
   - 具体操作描述
   - 工具/资源引用（绝对路径）
   - 产出物说明
3. **确认闸门**：使用 `> **确认闸门**` 引用块格式，明确用户确认后才能进入下一阶段

### 2.3 语法规范（必须）

| 规范项 | 要求 |
|--------|------|
| 资源引用 | 必须使用绝对路径，禁止相对路径 |
| 动作描述 | 必须使用编号列表，禁止段落文本 |
| 禁止事项 | 必须使用"禁止/必须"句式，禁止模糊建议 |
| 确认点 | 必须显式标注确认闸门 |
| 图示 | 禁止使用 ASCII 制图符号绘制框图，统一使用 Markdown 表格或列表结构 |

### 2.4 禁止使用的 ASCII 制图符号

以下字符及其组合禁止用于绘制框图、流程图等视觉结构：

```
禁止字符：┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ ╭ ╮ ╰ ╯ ─ │ ╱ ╲ ╳
替代方案：使用 Markdown 表格、mermaid 图表、有序/无序列表、引用块 (>)、缩进层级
```

## 三、核心要素体系

### 3.1 五要素模型（必须覆盖）

| 编号 | 要素 | 说明 | 示例 |
|------|------|------|------|
| 1 | 明确目标 (WHAT) | 要达成什么结果 | "在ESP32-P4上实现MIPI DSI屏幕驱动" |
| 2 | 执行流程 (HOW) | 分阶段的具体步骤 | 信息收集 -> 组件配置 -> 驱动开发 -> 测试验证 |
| 3 | 资源清单 (WITH) | 需要参考的文件/工具/组件 | 绝对路径列表 |
| 4 | 约束边界 (BOUNDARY) | 不能做什么、必须怎么交互 | "不直接执行ESP-IDF操作" |
| 5 | 验收标准 (CHECK) | 每阶段的确认点和完成标志 | "待用户确认信息完整后方可进入下一阶段" |

### 3.2 五大设计原则

| 原则 | 定义 | 验证方法 |
|------|------|----------|
| 渐进式 | 从简单到复杂，逐步推进阶段 | 检查阶段间是否存在能力依赖递增 |
| 可验证性 | 每个阶段有明确的产出物和验收标准 | 检查每阶段是否定义确认动作 |
| 资源明确 | 所有依赖资源路径清晰、可访问 | 检查所有文件引用是否为绝对路径 |
| 边界清晰 | 代理能做什么、不能做什么一目了然 | 检查是否存在"不直接执行XX"类声明 |
| 交互可控 | 关键决策点必须经用户确认 | 检查每阶段末尾是否有确认闸门 |

### 3.3 六大设计技巧

1. **阶段门控 (Stage Gate)**：前阶段确认后才进入下一阶段，防止跳过关键步骤
2. **资源显式绑定 (Explicit Resource Binding)**：绝对路径引用外部资源，避免猜测
3. **交互强制约束 (Interaction Enforcement)**：所有确认/提问必须通过交互工具（AskUserQuestion），禁止纯文字沟通
4. **角色边界定义 (Role Boundary)**：明确 Agent 与用户职责划分，Agent 不执行需物理操作的动作
5. **确认闸门 (Confirmation Gate)**：关键节点嵌入用户确认步骤
6. **子任务细化与迭代反馈 (Task Refinement & Feedback Loop)**：大任务细化为可验证子任务，支持闭环调整

## 四、应用场景

### 4.1 场景分类

| 场景类型 | 特征 | 建议阶段数 |
|----------|------|-----------|
| 嵌入式驱动开发 | 硬件依赖、多组件、需编译烧录 | 4阶段 |
| 系统集成 | 多方组件、配置复杂 | 3-4阶段 |
| 协议对接 | 标准文档多、参数精确 | 3阶段 |
| 调试诊断 | 错误复现、日志分析 | 3-4阶段（复现->诊断->修复->验证） |
| 功能开发 | 增量迭代、可测试 | 2-3阶段 |

### 4.2 触发条件

当满足以下 **任意两项** 时，必须启用 SOLO 模式：

1. 任务涉及3个以上独立步骤
2. 任务依赖外部参考资料或配置文件
3. 任务需要在多个决策点获得用户确认
4. 任务涉及用户本地环境的物理操作（编译、烧录、硬件连接）
5. 任务存在明显的阶段间依赖关系

## 五、约束规则

### 5.1 必须遵循的约束

| 编号 | 约束内容 | 违规后果 |
|------|----------|----------|
| S-C1 | 所有提问、确认、信息展示必须通过交互工具（AskUserQuestion）进行 | 用户无法确认，流程失控 |
| S-C2 | Agent 仅提供技术指导和流程控制，不直接执行需用户物理操作的动作 | 操作越权，无法执行 |
| S-C3 | 资源引用必须使用绝对路径 | 路径歧义，文件找不到 |
| S-C4 | 每个阶段末尾必须嵌入确认闸门 | 方向错误后无法纠正 |
| S-C5 | 禁止跳过阶段门控直接进入后续阶段 | 前置信息缺失导致失败 |
| S-C6 | 禁止使用 ASCII 制图符号绘制框图 | 渲染异常，可读性差 |

### 5.2 禁止事项清单

- 禁止使用纯文字形式代替交互工具进行确认沟通
- 禁止在未获用户确认的情况下进入下一阶段
- 禁止使用相对路径引用外部资源文件
- 禁止假设用户已完成前置操作（如组件下载、编译成功）
- 禁止在阶段中间插入与当前阶段无关的额外操作
- 禁止使用 ASCII 制图符号（`┌┐└┘├┤┬┴┼╭╮╰╯─│╱╲╳` 等）绘制框图、流程图

### 5.3 边界定义

| 边界类型 | 说明 |
|----------|------|
| 能力边界 | Agent 不执行编译、烧录、硬件连接等依赖用户物理环境的操作 |
| 决策边界 | 所有参数选择、配置决定权归用户，Agent 仅提供建议 |
| 阶段边界 | 阶段间不可跳跃，每阶段必须完成验证才能进入下一步 |

## 六、实施流程

### 6.1 任务初始化步骤

**步骤1：定义目标声明**
- 明确最终产出物
- 界定任务范围（做什么 + 不做什么）
- 输出：一句话目标声明（置于文档第1行）

**步骤2：设计阶段流程**
- 按依赖关系拆解为N个阶段
- 每个阶段定义：标题 + 动作清单 + 确认点
- 动作项中使用绝对路径引用资源
- 输出：编号的阶段流程（置于文档主体）

**步骤3：编写全局约束**
- 定义交互方式（必须用交互工具）
- 定义角色边界（Agent不做什么）
- 定义禁止事项
- 输出：约束段落（置于文档末尾）

### 6.2 阶段门控执行流程

1. Agent 进入当前阶段
2. Agent 执行阶段内动作清单
3. Agent 汇总产出物并通过交互工具展示给用户
4. 用户确认产出物完整准确
5. 确认通过 -> 进入下一阶段
6. 确认不通过 -> Agent 修正后重新展示

### 6.3 异常处理规则

| 异常场景 | 处理方式 |
|----------|----------|
| 某阶段失败 | 回退至上一阶段，检查前置条件是否满足 |
| 用户提供错误信息 | 通过交互工具提示修正，不自动推断 |
| 资源文件不可访问 | 提示用户检查路径，不尝试猜测替代文件 |
| 参数值缺失 | 要求用户提供精确参数，不使用默认值 |
| 用户要求跳过阶段 | 提示阶段门控规则，说明跳过风险，由用户最终决定 |

## 七、可复用模板

### 7.1 完整任务模板

```markdown
## 目标
[一句话描述最终要达成的结果，明确任务范围与边界]

## 阶段流程

### 阶段1：[阶段名称]
1. [动作项1：具体操作描述]
2. [动作项2：引用资源 `{绝对路径}`]
3. [动作项3：产出物说明]

> **确认闸门**：汇总以上产出物，通过交互工具向用户展示，待用户确认信息完整准确后方可进入下一阶段。

### 阶段2：[阶段名称]
1. [动作项1：具体操作描述]
2. [动作项2：引用资源 `{绝对路径}`]

> **确认闸门**：汇总以上产出物，通过交互工具向用户展示，待用户确认信息完整准确后方可进入下一阶段。

### 阶段N：[阶段名称]
...

## 全局约束
- 所有提问、确认和信息展示必须通过交互工具进行，禁止纯文字沟通
- Agent 仅提供技术指导和流程控制，不直接执行[具体禁止的操作类型]
- 所有资源引用必须使用绝对路径
- 每个阶段必须获得用户执行前确认和执行后验证
- 禁止使用 ASCII 制图符号绘制框图，统一使用 Markdown 表格或列表结构
```

### 7.2 轻量级单任务模板

当完整模板过于冗长时，可采用精简版，但必须保留核心要素：**目标声明 + 阶段拆分 + 确认闸门 + 全局约束**。

## 八、验证清单

在任务开始前，Agent 必须逐项确认：

- [ ] 目标声明已包含任务范围与边界
- [ ] 阶段数量与任务复杂度匹配（建议3-4阶段）
- [ ] 每阶段有明确的动作清单
- [ ] 每阶段有明确的确认闸门
- [ ] 所有文件引用均为绝对路径
- [ ] 全局约束包含交互方式声明
- [ ] 全局约束包含角色边界声明
- [ ] 未使用任何 ASCII 制图符号
- [ ] 未使用相对路径引用
