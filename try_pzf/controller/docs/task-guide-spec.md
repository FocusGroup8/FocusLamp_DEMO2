# 普通模式 · 三步任务引导 · 实施规格 v4（现场修补）

2026-10-31。首版代码及现场修补已编译；这不代表真机功能已验收。测试记录见 `tools/task-guide/`。尚未烧录或完成真机验收。
本版取代 v2 中的触摸轮询、epoch 比大小及 ASSISTANT 文本拼接方案。

## 1. 用户流程

普通模式（实际为 `APP_STATE_IDLE`，也兼容 `APP_STATE_COMPANION`）中说“帮我拆解一下整理桌面的任务”：

1. AI 通过 MCP 提交三条具体、易懂的动作，每条 1–18 个 Unicode 字符。
2. 屏幕先展示三条，等待点击，不计时。
3. 一次完整的屏幕按下—松开后进入第一步，只显示当前一步与圆环、剩余时间。
4. 每步 180000 ms，自动进入下一步，总计九分钟；说话不暂停。
5. 运行期间再次完整点击，立即本地退出，返回表情，不跳步。
6. 第三步计时结束显示“本轮引导结束”两秒，返回表情；不声称任务实际已完成。

首次点击不会同时开始和退出。若用户确实完成了第二次点击，即使紧接第一次，也应该退出；没有 800ms 屏蔽。

## 2. 设备职责与断网

- head 是唯一计时源，使用单调时钟，从起始时刻计算各阶段，不卡帧累积误差。
- controller 负责用户请求门控、MCP 校验、内容下发和记录 head 状态，不倒推/覆盖 head 剩余时间。
- 进入预览后无需继续联网；断网照常推进，屏幕点击仍立即本地退出。
- head 保留最新报告，恢复连接后上报；controller 端按 `report_seq` 去重，终态不被旧报告复活。
- 收到成功读取的非普通模式快照时退出引导；网络读取失败不是退出依据。
- head 重启不恢复进行中的引导。首个快照若已经是 ready，则按旧结果基线丢弃并上报 dismissed；用户重新提出任务即可。
- 尚在预览或运行中时，不接受另一份拆解覆盖。先点击开始/退出或等计时结束，再提出新任务。

## 3. 防止迟到结果重弹

不能仅靠“更大的 epoch”认定新任务：必须由新的用户语音或网页文字请求打开等待窗口。

- USER STT 中明确包含拆解/拆分/分解意图及“帮我/任务/三步”等请求措辞，或“清理桌面分3步，提醒我怎么做”等明确请求，且当前为 idle/companion，才创建新请求。
- `self.task_guide.pending` 只读，不能创建请求；返回当前 request_token 及原始任务。
- `self.task_guide.set` 必须原样携带令牌；不是 AI 自行生成编号。
- 请求身份为 controller boot ID + request ID；旧令牌、超时令牌、已退出令牌不可提交。
- 等待期间新的用户话轮会使旧等待失效；普通聊天不会中止已经下发/运行的引导。
- 退出后同一 ready 快照不重新打开。新请求只能由用户重新发起。

等待超时默认 30000 ms，通过 `CONFIG_TASK_GUIDE_WAIT_TIMEOUT_MS` 可配置。已观察到等待请求的 head 收到 timeout 后显示四秒中性提示：
“暂时没收到结果 / 再说一次试试”。没有本地 TTS 播报承诺。完全断网时无法接收 controller 的超时提示。

## 4. AI 与三条校验

主通道是 MCP 结构化数组，不解析逐句口语回复：

1. 语音入口用 `self.task_guide.pending()` 获取请求令牌；网页 `/api/tts/speak` 的明确任务请求在队列真正提交时打开窗口，并附加令牌和调用规则。
2. `self.task_guide.set({request_token, steps:[s1,s2,s3]})` 提交。

双方共享 `shared/task_guide_protocol.h`：正好三条，严格 UTF-8、每条 1–18 字符、无换行/控制字符、无编号前缀/Markdown、无首尾空白、互不重复。
不合格返回工具错误，仍在等待有效期内可以修正；过期不自动开启新请求。

底层 TTS sentence_start 本来就发出 ASSISTANT 文本；manager 只向上转发 USER STT。它不是本功能的阻塞项。本版不新增没有消费者的整段文本收集。
HTTP 增强提示在临时 PSRAM 中生成，绕开短文本队列的 255 字节限制，不扩大八项队列，也不把增强提示截断；提交失败取消对应等待请求。确切回声不再打开新请求。
云端角色说明推荐片段及确切工具调用见 `task-guide-integration.md`；本轮没有修改云端角色。

## 5. 屏幕与触摸

- GT911 已由 `board_init.c` 初始化，并由 `lvgl_display.c` 注册为 LVGL 输入；表情模式也使用该路径。
- 补的是表情画布的 PRESSED/RELEASED/PRESS_LOST 事件，不新建 GT911 轮询器，不与现有读触摸通道争用。
- 开始前按下、任务到达后才松开，不算有效点击；按下/松开必须属于当前同一请求。
- 引导之外不消费点击，不改变现有 TTP223 操作。TTP223 与 GT911 是不同输入，不能混称屏幕触摸。
- GT911 注册不可用时，丢弃不可操作的预览并打印日志，而不是显示无法点击的界面。

文字：16px 单色 Noto Sans SC OFL 字库，3864 字形（GB2312 一级、ASCII、UI 补字），静态数据 131376 字节位于 flash，不复制整库到 RAM。
中文 16px / ASCII 8px，最长 18 字分两行时尽量均衡。未知字画方框并有限记录，不静默留白。
所有文本、圆环复用现有 RGB565 画布，无额外全屏缓冲；实际字体大小仍需真机观察。
同步响应缓冲扩至 3072 字节，对应 worker 栈从 6144 增至 10240 字节，避免三条文本扩大响应后截断/挤占栈。

## 6. HTTP 协议

`GET /api/mode` 保留原有字段，附加：

```json
{"task_guide":{"controller_boot_id":17,"request_id":1,"state":"ready","wait_timeout_ms":30000,"steps":["丢掉桌面垃圾","把物品分类放好","擦净桌面并摆回常用品"]}}
```

state 为 idle / waiting / ready / timeout / dismissed / done；仅 ready 带 steps。
head 只在完整且成功的响应后处理。原有专注数据同步逻辑保留。

`POST /api/mode/task_guide` 是状态记录，不是远程计时指令：

```json
{"controller_boot_id":17,"request_id":1,"state":"running","step":0,"remaining_ms":180000,"report_seq":2}
```

state 为 preview / running / done / dismissed，step 为 0–2。状态改变及运行期间约五秒上报一次；失败保留最新报告重试，不影响本地操作。

## 7. 验收

主机验证覆盖协议校验、请求令牌/超时/模式门控、预览不计时、三分钟边界、九分钟结束、离线计时、快速第二次点击退出、无按下的重复松开无效、退出后不重弹、模式切换取消、中文字形/裁剪/stride。

真机仍需：

1. 两板烧录新固件，普通模式下说任务，确认 MCP 工具被实际调用。
2. 查看三条文字是否清晰完整，点击开始，观察圆环与倒计时。
3. 验证各步三分钟、第三步结束、点击退出和普通聊天不暂停。
4. 开始后断网，继续计时并点击退出，恢复后不重弹。
5. 检查 GT911 实际按下/松开灵敏度、画面帧率和中文字号。
